## TASK A — VERIFICATION FINDINGS

### 1. CSP Nonce Verification ⚠️ CRITICAL ISSUE

**Current Implementation** (`src/middleware.ts` line 25):
```
script-src 'self' 'nonce-NEXT_PUBLIC_CSP_NONCE';
```

**Issue**: The CSP directive uses the **literal string** `'nonce-NEXT_PUBLIC_CSP_NONCE'` as the nonce value. This is **not how CSP nonces work** in Next.js (or any browser).

**How CSP Nonces Should Work**:
1. A cryptographic nonce is generated **per-request** by the server.
2. The **same nonce** is injected into each `<script>` tag rendered by the framework (Next.js does this automatically for App Router).
3. The browser only executes scripts whose nonce **matches** the one in the `script-src` directive.

**What Is Happening Here**:
- The header contains the literal string `"nonce-NEXT_PUBLIC_CSP_NONCE"` as the nonce value.
- Next.js App Router **does not** inject a nonce matching this literal string into its `<script>` tags.
- Result: **All scripts are blocked** by the CSP, including Next.js's own hydration scripts, React framework scripts, and any application JavaScript.
- **Impact**: The application will experience broken hydration, missing interactive components, console errors, and potentially a white screen.

**Is the nonce**:
- ✅ Dynamically generated? **No** — it's a static literal string.
- ✅ Cryptographically unpredictable? **N/A** — it's hardcoded.
- ✅ Unique per response? **No** — it's the same on every response.
- ✅ Exposed through `NEXT_PUBLIC` env var? **No** — it's hardcoded in source.
- ✅ Attached to actual Next.js-rendered scripts? **No** — Next.js injects its own nonces that don't match this literal.
- ✅ Propagated through middleware headers correctly? **Technically yes** (the header is set correctly), but the **value** is wrong.

**Immediate Correction Required**:

**Option A — Remove the nonce from `script-src` and rely on `'self'` only** (recommended for immediate fix):

```
script-src 'self';
```

**Pros**: Immediately fixes the broken CSP; scripts work immediately.
**Cons**: Loses the added security of nonce-based script restriction; any future inline scripts would need `'unsafe-inline'`.

**Option B — Implement Proper Next.js Nonce Integration**:

1. In `_document.tsx` (or via `next/head`/`next/script` components), Next.js will automatically inject nonces into `<script>` tags.
2. The CSP `script-src 'self' 'nonce-...'` must reference the **actual nonce generated by Next.js**, not a hardcoded string.
3. Next.js makes the nonce available via the `{nonce}` attribute on `next/script` components or through the document's `_document.tsx` `securityTags` function.

**Pros**: Full nonce-based security; blocks inline scripts without matching nonce; future-proof.
**Cons**: Requires modifying `_document.tsx` or ensuring `next/head`/`next/script` are used correctly; breakage if not done exactly right.

**Option C — Remove `'nonce-NEXT_PUBLIC_CSP_NONCE'` and use `'unsafe-inline'` for scripts (last resort)**:

```
script-src 'self' 'unsafe-inline';
```

**Pro**: Scripts work immediately.
**Con**: Defeats the purpose of having a CSP script directive; opens XSS risk from inline scripts.

### 2. CORS Verification ✅ PASSING

**Verification Checks**:

| Check | Status | Evidence |
|---|---|---|
| No wildcard origins (`*`) exist | ✅ Pass | All route wrappers set `Access-Control-Allow-Origin` to specific origin or omit it entirely. |
| Production does not accidentally allow development origins | ✅ Pass | Dev origins (`localhost:3000`, `127.0.0.1:3000`) are only set in route wrappers when the request's origin matches; production origins are not configured (same-origin default). |
| No combination of wildcard + credentials | ✅ Pass | `Access-Control-Allow-Credentials: true` is ONLY set when origin is a known dev origin; middleware explicitly avoids `Access-Control-Allow-Origin: *`. |
| OPTIONS preflight handling | ✅ Pass | Middleware's `corsPreflight` function handles OPTIONS requests; route wrappers handle their own CORS for non-preflight requests. |
| Authentication still enforced | ✅ Pass | All API routes check `session?.user?.id` before processing; CORS headers are added after auth check. |

**CORS Architecture Summary**:
- **Default**: Same-origin (middleware has empty `allowedOrigins`).
- **Development**: Route wrappers (`/api/auth`, `/api/register`, `/api/scan/*`) set `Access-Control-Allow-Origin` to the request's origin if it matches `localhost:3000` or `127.0.0.1:3000`.
- **Production**: No origins configured → same-origin only, which is correct for the typical deployment model (frontend and API on same domain/port).
- **Credentials**: `Access-Control-Allow-Credentials: true` is ONLY set when the origin is a known dev origin; never set to `true` with a wildcard.
