# Implementation Report: P1-CRITICAL-002 — Stored XSS Security Remediation

## 1. Investigation — Vulnerable Rendering Paths

### 1.1 Dashboard Scan History Table

**File:** `src/app/dashboard/page.tsx`

The dashboard displays scan history in a table. Several columns render user-controlled input directly:

```tsx
<td className="font-mono text-sm text-gray-300 max-w-md truncate block">{s.input}</td>
```

This renders the raw scan input (URL, message text, email content, or QR payload) as-is. If a user scanned a URL containing `<script>` tags or event handlers, those would be rendered as raw HTML in the browser because React text interpolation `"{s.input}"` preserves the string content, but when the string contains HTML tags and is placed inside `td` elements, browsers render them.

Similarly:

```tsx
<td><span className="badge" style={{ borderColor: classColors[s.classification], color: classColors[s.classification], backgroundColor: classColors[s.classification] + "20" }}>{s.classification}</span></td>
```

The classification is from a controlled enum (SAFE/SUSPICIOUS/MALICIOUS), so it's safe.

But `s.input` is user-controlled data from scan submissions.

```tsx
<td className="font-mono text-sm text-gray-300 max-w-xs truncate block">{s.input}</td>
```

Also:

```tsx
<td className="text-gray-300">{s.user?.email || "Unknown"}</td>
```

User email is from the database, which could also be user-controlled during registration, but the registration form has basic validation. Still, it's user-controlled data.

## 2. Root Cause

The root cause is **missing output encoding** for user-controlled data when it is rendered into the DOM. 

React protects against XSS for **simple text interpolation** — when you write `{someVariable}` in JSX, React automatically escapes HTML special characters (`<`, `>`, `&`, `"`, `'`). This means most basic XSS is prevented.

However, the vulnerabilities here are not from naive `{variable}` interpolation but from:

1. **CSS inline styles** that include user data — not currently present, but a pattern to watch.
2. **`dangerouslySetInnerHTML`** — not found in the codebase, but the risk exists if added later.
3. **Rendering user data in `style=` attributes** — not currently present.
4. **Future additions** of Markdown rendering, HTML content display, or user profile customization without proper escaping.

The specific paths where `s.input` (and similar user-controlled data) is placed into the DOM via JSX text interpolation `{s.input}` are actually safe **as long as React's default escaping is in effect** (which it is). However, the risk is **real if**:
- The data is later placed into `innerHTML`, `dangerouslySetInnerHTML`, or `style=` attributes.
- A future React upgrade or configuration change disables automatic escaping.
- Third-party libraries are introduced that render the data unsafely.

**The more practical concern** is not the current XSS but the **potential** for XSS if the application evolves to display user content as HTML, or if the detection engine descriptions/reasons ever become user-controllable.

## 3. Remediation

### 3.1 Strategy: Preserve Safe React Rendering, Add Sanitization Where HTML Is Genuinely Needed

The remediation approach is:

1. **Keep using React text interpolation** — it's already safe for plain text. No changes needed for the basic `{s.input}` patterns.
2. **Add HTML sanitization** for any case where user content might eventually be rendered as HTML, or where the detection results might contain user-influenced text.
3. **Sanitize URLs** before rendering them as clickable links (ensuring `href` only contains `http:` or `https:`).
4. **Do NOT sanitize** the detection engine's internal descriptions/reasons — they are generated by the code, not users, and sanitizing them would destroy forensic information.
5. **Normalize user-generated names/emails** during registration/login to strip dangerous characters, but keep the data visible.

#### 3.2.2 Admin Users Table

Same — `u.name` and `u.email` are rendered via React text interpolation, which is safe. No changes needed.

However, we can add **input normalization during registration** to limit the character set of names, preventing extreme edge cases. The registration route already validates with Zod:

```ts
const schema = z.object({ name: z.string().min(1), email: z.string().email(), password: z.string().min(6) });
```

We can tighten the name validation to allow only safe characters (alphanumeric, spaces, hyphens, apostrophes):

```ts
const schema = z.object({ 
  name: z.string().min(1).regex(/^[a-zA-Z0-9\s\-'.]+$/, "Name must contain only letters, numbers, spaces, hyphens, apostrophes, and periods"), 
  email: z.string().email(), 
  password: z.string().min(6) 
});
```

This prevents names from containing `<`, `>`, `"`, `'`, `/`, `\`, etc., which are the characters most likely to be used in XSS attacks.

### 9. Recommendations

1. **The core XSS risk is already mitigated** by React's automatic escaping. The changes made (name regex) are defense-in-depth, not fixes for active vulnerabilities.

2. **If the app ever adds rich-text display** (e.g., showing scan reason descriptions in bold/italic, or user profiles with custom formatting), implement HTML sanitization using a library like `dompurify` or a custom sanitizer that allows only a whitelist of tags/attributes.

3. **If Markdown is ever added for scan notes or user posts**, use a sanitizing renderer:
   ```ts
   import markdown from "remark-gfm";
   import { sanitize } from "hast-util-sanitize";
   const html = markdown.parse(input);
   const safeHtml = sanitize(html, { allowedTags: ["b", "i", "strong", "em", "a"], allowedAttributes: {} });
   ```

4. **Keep the name regex** even though React escaping is active — it's a cheap, zero-runtime-cost defense that reduces the attack surface if escaping is ever bypassed or disabled.

5. **Document this remediation** in the codebase (done via the implementation report and comments in the source files).

6. **No changes are needed to the detection engines** — they produce plain-text descriptions and are not modified.

7. **No changes are needed to the API routes** — they return JSON, and the JSON is rendered via React text interpolation on the frontend.

8. **Monitor** — if the app evolves to display user-generated HTML (e.g., user profiles, rich scan notes), add a follow-up security review.
